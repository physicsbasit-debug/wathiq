# Phase 0-E — قرار التخزين المركزي

## القرار

اعتماد **Supabase** لسجل المصادر المركزي في المرحلة الحالية.

## لماذا Supabase؟

- بيانات واثق مترابطة بطبيعتها: مستخدمون، مصادر، إصدارات، وحدات، نواتج تعلم، خطط اختبارات، واشتراكات.
- PostgreSQL مناسب لهذا النموذج أكثر من بناء مجموعات وثائق متفرقة ثم محاولة إقناعها بأنها علاقات.
- Row Level Security يسمح بحماية السجلات وفق المستخدم من داخل قاعدة البيانات.
- Data API يسمح لواجهة GitHub Pages بالاتصال مباشرة باستخدام مفتاح Publishable منخفض الصلاحيات مع جلسة المستخدم.
- يمكن التوسع لاحقًا إلى Storage وEdge Functions دون تغيير قاعدة البيانات الأساسية.

## القرار الأمني

- لا يُستخدم مفتاح Secret أو Service Role داخل المتصفح أو GitHub Pages.
- يستخدم التطبيق مفتاح Publishable فقط.
- الوصول إلى البيانات يتطلب تسجيل دخول Supabase Auth.
- كل سجل يحمل `owner_id`، وسياسات RLS تسمح للمستخدم بقراءة وتعديل سجلاته فقط.
- صلاحيات `anon` على جدول المصادر ملغاة.

## حدود المرحلة

- حساب مالك واحد عمليًا في Phase 0-E.
- لا أدوار معلمين أو اشتراكات في قاعدة البيانات بعد.
- لا تخزين لملفات PDF نفسها.
- لا Google Drive ولا فهرسة محتوى.

## التوسع اللاحق

عند إضافة حسابات المعلمين، ستُفصل صلاحيات مالك المنصة ومدير المحتوى عن صلاحيات المعلم، ولن تبقى سياسة المصادر مبنية على وجود مستخدم مصادق فقط.
