# Phase 2-D4 — Progressive Generation UI and Resume

## الهدف

ربط نواة D1، ومنظومة المهام الدائمة D2، وعامل المفردة D3 بواجهة الإنتاج، بحيث تعمل كل مفردة كمهمة مستقلة محفوظة خادميًا، وتظهر نتائجها تدريجيًا، ويمكن استكمال الدورة بعد تحديث الصفحة دون إعادة المفردات الناجحة.

## التدفق الإنتاجي

```text
إعداد الاختبار
→ بناء الخطة والمخطط الحتمي
→ بناء عقد مستقل لكل مفردة
→ enqueue دورة دائمة
→ تشغيل عاملين بحد أقصى
→ حفظ نتيجة كل مفردة خادميًا
→ دمجها فورًا في المسودة
→ مراجعة عامة حتمية
→ مهام الصور اللاحقة
→ المراجعة والتصدير
```

## مكونات الواجهة

### `assessment-generation-progressive.ts`

مسؤول عن:

- تحويل خطة المسودة إلى `AssessmentBlueprint`.
- إنشاء `AssessmentItemContract` لكل مفردة.
- تثبيت المصدر الصريح وبصمته.
- توزيع التنوع والسيناريو والنمط والمرئي.
- حماية المرئيات الضرورية علميًا.

لا يتصل هذا الملف بالشبكة أو DOM أو التخزين.

### `assessment-generation-orchestrator.ts`

منسق خفيف مسؤول عن:

- إنشاء الدورة أو استعادتها.
- polling للحالة الدائمة.
- تشغيل مهمتين متزامنتين كحد افتراضي.
- عدم إرسال العناصر `ready`.
- مهلة تهدئة بعد إرسال العامل أو تعذر الشبكة.
- التوقف المحلي دون العبث بنتائج الخادم.

لا يولد سؤالًا، ولا يقرأ مصدرًا، ولا يطبع نتيجة Gemini.

### `app.ts`

مسؤول عن:

- الانتقال الفوري إلى صفحة التقدم.
- بناء الحمولة وربط الخدمات.
- دمج النتائج الجاهزة في `PlanItem`.
- تحديد الاقتراح الوحيد وحفظ checkpoint.
- عرض الحالات والتقدم والأخطاء.
- إعادة المفردة الفاشلة أو إلغاء الدورة.
- الاستكمال بعد مزامنة المصادر.
- بدء الصور بعد اكتمال الأسئلة.

## حالة المسودة

أضيف إلى `ExamDraft`:

```ts
generationRunId: string;
generationEpoch: number;
```

ويستخدم النمط:

```text
progressive_items_v1
```

`generationEpoch` هو حاجز ضد النتائج المتأخرة. أي تغيير جوهري في المحتوى أو الخطة يلغي الدورة ويرفع الإزاحة.

## التوازي

القيمة الافتراضية:

```text
2
```

يحسب المنسق عدد العناصر النشطة خادميًا، ثم يرسل من `queued` أو `retry_pending` بما يكمل الفتحتين فقط. لا تعتمد الحماية على ذاكرة المتصفح وحدها؛ claim في D2 هو الحارس النهائي ضد التكرار.

## الدمج التدريجي

عندما تصبح المهمة `ready`:

1. تُقرأ `result` من لقطة الدورة.
2. تتحول إلى `QuestionProposal` واحد.
3. يضاف العقد العلمي والمرئي والدليل الخادمي.
4. يُختار الاقتراح تلقائيًا.
5. تحفظ المسودة فورًا.

المفردات الأخرى تستمر دون انتظار.

## الاستكمال

عند فتح مسودة تحمل `generationRunId`:

- لا تنشأ دورة جديدة مباشرة.
- تستدعي الواجهة `list`.
- تتحقق من الإزاحة والبصمات.
- تستدعي `resume` إذا كانت الدورة مطابقة.
- تنشئ دورة جديدة فقط إذا لم توجد دورة مطابقة.

## الفشل والإلغاء

- `retry`: يعيد مهمة واحدة فاشلة إلى الطابور وفق حدود D2.
- `cancel`: يلغي الدورة خادميًا ويحفظ النتائج الجاهزة.
- تسجيل الخروج يوقف المنسق المحلي، ولا يحذف النتائج الخادمية.
- حذف المسودة النشطة يوقف المنسق ويلغي دورتها best-effort.

## فحص العامل

قبل إنشاء أو استعادة دورة، تستدعي الواجهة:

```text
assessment-generation-worker / health
```

وتتحقق من:

```text
engineSchemaVersion = 1
contractVersion = 1
```

هذا يمنع إنشاء طابور دائم لا يملك عاملًا متوافقًا لمعالجته.

## الحدود المرحلية

- ملفات المحرك السابق لم تُحذف في D4 لأن التخزين والاختبارات التاريخية ما زالت تقرأ مسوداته المكتملة.
- لا يوجد fallback إنتاجي إليه في `app.ts`.
- لا تنقل D4 run من `reviewing` إلى `completed` خادميًا؛ المسودة هي التي تنتقل للمراجعة بعد اكتمال العناصر. يمكن إغلاق هذه الفجوة الإدارية في مرحلة القطع والتنظيف دون تأثير على توليد الأسئلة.
- زمن Gemini نفسه غير مضمون؛ D4 تمنع إعادة العمل وانتظار الاختبار كاملًا، ولا تدعي التحكم في مزود خارجي.

## اختبار القبول

يشترط قبل الإغلاق التشغيلي:

- تقدم فوري ومرئي.
- حد تزامن 2.
- ظهور النتائج تدريجيًا.
- استكمال بعد refresh.
- عدم إعادة `ready`.
- إعادة المفردة الفاشلة وحدها.
- استمرار التصدير والاعتماد.
