# معمارية واثق 0.3.19

## خط أساس الاستعادة 0.3.16

هذه النسخة تثبت النواة الكاملة التي كانت قائمة قبل انحراف Wathiq 2.0. لا يجوز استبدال الواجهة أو Blueprint/Contracts بطبقات تجريبية أو stubs لإرضاء اختبارات نصية. أي تفكيك معماري لاحق يجب أن يحافظ على المسار القابل للتنفيذ End-to-End ويحدّث `runtime:check` صراحة ضمن المرحلة نفسها.

## المبدأ

واثق يبدأ من **الصف / المرحلة ثم مادة العلوم ثم موضوع كامبريدج من قائمة مرتبطة بالاختيار**. لا توجد طبقة رفع مصادر في النواة الحالية، ولا يحتاج المستخدم إلى كتاب أو دليل معلم حتى يحصل على اختبار.

```text
الصف / المرحلة
→ مادة العلوم
→ موضوع أو عدة موضوعات من قائمة كامبريدج
→ سياق عالمي مناسب للبرنامج والمرحلة/السيلابس
→ مؤلف حر بعقد مفردة نصي نحيف + visualIntent
→ مراجع علمي وتقويمي مستقل بالعقد النحيف نفسه
→ قرارات عرض الطالب: المثير الضروري فقط + نوع المرئي إن وجد
→ محققات علمية حتمية قابلة للتوسع
→ مرئي غير رقمي: أصل 2D علمي مدقق
→ جدول/رسم بياني: Visual Planner للبيانات المرئية للطالب فقط → Renderer حتمي
→ مراجعة وتصدير
```

## جدول المواصفات قبل التأليف

المواصفة الرسمية طبقة حتمية **قبل** الذكاء الاصطناعي. يحدد المحرك نوع كل مفردة ودرجتها وهدف التقويم ومستوى الصعوبة حيث يلزم، ووسم الاستقصاء العلمي عند الحاجة. بعد ذلك يملك المؤلف حرية صياغة السؤال داخل هذا العقد فقط. لا توجد حقول يدوية لتغيير الدرجة أو عدد المفردات بما يكسر المواصفة.

في الصف العاشر للفيزياء، قائمة الموضوعات في الواجهة مستمدة من فهرس الكتاب المحلي المرفوع (19 وحدة، 46 موضوعًا/درسًا)، بينما يبقى سياق التأليف علميًا كامبريدجيًا عالميًا.

## التأليف والمراجعة

يبني واثق سياق الدرس من البرنامج والمرحلة أو السيلابس والمادة والموضوع. لا يختلق هدفًا رسميًا منسوبًا إلى كامبريدج؛ بل يكوّن سياقًا علميًا وتقويميًا مناسبًا للمستوى ويطلب من المؤلف إنشاء أفضل مفردة ممكنة ضمن نطاق الموضوع.

المؤلف حر في اختيار السياق والمثير وبنية السؤال. يعيد المؤلف عقدًا **نحيفًا** يضم النص والبدائل والإجابة والتفسير ونقاط التصحيح و`visualIntent` فقط، ولا يحمل هندسة الرسم أو بياناته التفصيلية. بعده يعمل مراجع مستقل بالعقد النحيف نفسه، يفحص الصحة العلمية وملاءمة المرحلة ووضوح السؤال وجودة المشتتات والإجابة ونموذج التصحيح، ويستطيع إعادة كتابة المفردة عند الحاجة.

التحقق الحتمي لا يحكم جودة اللغة أو المعنى. يستخدم فقط عندما يستطيع البرنامج إثبات النتيجة مثل مجموع الدرجات، بنية الخيارات، البيانات العددية، وبعض العلاقات الحسابية والبصرية الدقيقة.


## ضمان Visual Job الخادمي — 0.3.19

- إذا كانت نتيجة المفردة تحمل `context_scene`، يستدعي `assessment-generation-worker` خدمة `question-visual-jobs` بنفس جلسة المستخدم قبل استدعاء `complete_assessment_generation_item`.
- لا يجوز أن تصبح المفردة `ready` إذا لم تُرجع خدمة الصور مهمة تحمل `planItemId` نفسه و`requiredMode=replace`.
- فشل الشبكة/الخدمة أو `jobs=[]` يصنف كتأجيل تشغيلي ويعيد المفردة إلى `retry_pending` دون احتساب فشل محتوى.
- المتصفح لم يعد مالك إنشاء المهمة؛ وظائف `scheduleContextSceneVisualJobSync` و`syncVisualJobs` تبقى للمزامنة والاستعادة والتوافق مع المسودات القديمة.

## المرئيات الحالية — 0.3.18

- كل مرئي علمي غير رقمي يستخدم أصلًا ثنائي الأبعاد كاملًا (`illustration_2d` → `context_scene`) ثم يراجع علميًا وبصريًا قبل الاعتماد.
- اقتُلع مولد الرسوم التخطيطية الخطية القديم؛ لا توجد في مسار الإنتاج أنواع force/circuit/electrostatic/ray/pressure/flow/instrument-scale.
- `data_table`, `line_graph`, `bar_chart` فقط تبقى تمثيلات حتمية لأن واثق يملك القيم والمحاور الدقيقة.
- Visual Planner للبيانات لا يرى الإجابة أو نموذج التصحيح، ومراجع الصورة يفرض `noAnswerLeakage`.
- عند تعذر أصل 2D تظهر حالة فشل/إعادة توليد؛ لا يوجد fallback خطي يخفي الفشل.

## التخزين والحساب

Supabase مسؤول عن الجلسة، المسودات، مهام التوليد الدائمة، ومهام المرئيات. بعض أسماء الحقول الداخلية في مخطط التوليد تمثل **لقطة سياق التوليد**؛ لا توجد جداول رفع ملفات أو فهرسة محتوى في المخطط الحالي.

## العربية واتجاه الواجهة

`index.html` يثبت `lang="ar"` و`dir="rtl"` من الجذر. كل شاشة وحقل وحالة ورسالة وتقرير وتصدير للمستخدم عربي وRTL. يسمح باتجاه يسار إلى يمين فقط لرمز تقني أو قيمة رقمية/محور يحتاجه ذلك صراحة.

رسائل المزود الخارجية لا تمر إلى المستخدم كما هي؛ الواجهة تعرض رسالة عربية آمنة وتبقي التفاصيل التقنية خارج واجهة المستخدم.

## منع الأحافير

`npm run legacy:check` يفحص كود التشغيل ووظائف Edge والمخطط الحالي، ويرفض رجوع مسارات Google Drive/OAuth/OCR، منظومة المصادر، المحركات القديمة، العقود الصلبة، أو بدائل الرسم الخطي.

`npm run ui:check` يتحقق من العربية وRTL، عدد عناصر التنقل الحالي، RTL في التصدير، ومنع رسائل المزود الإنجليزية المعروفة من التسرب إلى الواجهة.

## حراس الجودة الجذرية

- **المثير** جزء مستقل عن stem، ولا يبقى في ورقة الطالب إلا إذا كان يحمل بيانات أو موقفًا لازمًا للحل. الشرح العلمي ونموذج التصحيح لا يدخلان محتوى الطالب.
- **المرئي** له قرار واحد فقط: `none` أو `context_scene` 2D أو جدول/رسم بياني حتمي. لا توجد طبقة `helpful/required` ولا مولد تخطيطي خطي في العقد الحالي.
- **Science Validation Adapters** طبقة دفاع حتمية بعد المراجع الذكي وقبل الحفظ، وتتكرر في واجهة الاعتماد لمنع تمرير مسودة قديمة فيها تناقض معلوم. أول Adapter يغطي تناقضات كهرباء ساكنة قابلة للكشف يقينًا.
- **ورقة الطالب** لا تعرض حالات تشغيل داخلية أو placeholder بصريًا أو ملاحظات المراجع. **نسخة المعلم** تحافظ على الإجابة ونقاط التصحيح والتفسير العلمي.

## 2D Visual Reset — 0.3.18

المسار الحالي يلغي التنفيذ التخطيطي الذي بدأ في v0.3.6–0.3.14 للمشاهد العلمية. تبقى تلك الأقسام أدناه كسجل تاريخي فقط ولا تصف runtime الحالي.

```text
visualIntent
├─ none → لا مرئي
├─ illustration_2d → context_scene → question-visual-jobs → science-visual-generation → مراجعة 2D → Storage
├─ data_table → Visual Planner (student-visible only) → Renderer حتمي
├─ line_graph → Visual Planner (student-visible only) → Renderer حتمي
└─ bar_chart → Visual Planner (student-visible only) → Renderer حتمي
```

- لا يرى Visual Planner `answer` أو `markScheme`.
- لا يسمح Worker بأنواع الرسوم التخطيطية القديمة.
- قارئ المسودات يحول النوع القديم إلى `context_scene` عبر جسر ترحيل للقراءة فقط، ثم يهمل هندسته القديمة.
- لا Migration SQL؛ visual JSON مرن أصلًا.

## المرئيات العلمية الدقيقة (v0.3.6)

- المشهد السياقي الحر فقط (`context_scene`) يمر عبر `science-visual-generation` ونموذج الصور.
- الرسوم التي تحمل معنى علميًا دقيقًا أو بيانات لا تُفوَّض إلى نموذج الصور: `force_diagram`, `circuit_diagram`, `electrostatic_diagram`, `ray_diagram`, `pressure_diagram`, `flow_diagram`, إضافة إلى الجداول والرسوم البيانية وتدريج الأجهزة.
- منذ v0.3.14 لا يحمل عقد المؤلف/المراجع البيانات الهندسية التفصيلية. بعد اعتماد النص، يطلب واثق من **Visual Planner متخصص بالنوع** البيانات اللازمة فقط (`vectors/anchors/segments/dimensions` للقوى مثلًا)، ثم يرسمها العميل حتميًا SVG، فتظل القيم والوحدات والاتجاهات مطابقة للسؤال دون تضخيم Structured Output الرئيسي.
- في مخطط القوى، إذا وردت قيم بوحدة N في نص الطالب فيجب أن تظهر ضمن متجهات المرئي قبل اعتماد المفردة.
- لا توجد نسبة صور مفروضة؛ القرار التأليفي يبقى حرًا، لكن نوع المرئي يتحدد بحسب ما إذا كان سياقيًا أو يحمل بيانات علمية حاكمة.
## اتساق المرئيات الميكانيكية ونسخ الواجهة (v0.3.7)

- المرئيات الميكانيكية الدقيقة لا تعتمد على صورة Gemini. مواصفة `force_diagram` قد تحمل هندسة normalized 0–100 عبر `segments` و`anchors` و`dimensions` مع `vectors`.
- `assessment-generation-worker` ينسق مخطط المرئيات المتخصص المسؤول عن إنتاج الهندسة العلمية اللازمة للحل؛ مسائل العزم لا تمر دون ساق/قضيب ونقطة ارتكاز، والمسافات العددية اللازمة يجب أن تظهر في `dimensions`.
- `question-visual-jobs` يقبل `context_scene` فقط. أي مخطط منظم يصل إليه من عميل قديم لا يرسل إلى `science-visual-generation`.
- البناء يضيف رقم الإصدار إلى graph وحدات ES في `dist` حتى لا يجمع المتصفح `app.js` قديمًا مع `question-visual.js` جديدًا أو العكس بعد نشر GitHub Pages.


## عقد القرار البصري الواحد (v0.3.8)

- حُذف `QuestionVisualRequirement` من عقد التطبيق؛ نوع المرئي نفسه هو القرار الوحيد.
- يحتفظ قارئ المسودات بالتوافق الخلفي: إذا وجدت مسودة قديمة حقل `requirement` فإنه يُتجاهل ولا يعاد حفظه في العقد الحالي.
- `none` يعني لا مرئي. الأنواع المنظمة مثل `force_diagram` و`data_table` تُرسم مباشرة ولا تنشئ مهام صور.
- `context_scene` يعني أن المؤلف اختار مشهدًا سياقيًا جزءًا من المفردة؛ لذلك تنشأ له مهمة صورة 2D واحدة من مسار الصور الدائم، ويمنع الاعتماد/التصدير حتى يرتبط أصل مدقق بالمفردة.
- لا توجد بوابة مستقلة تقرر بعد التأليف إن كان الرسم «مساعدًا» أو «إلزاميًا». هذا يمنع التناقض بين قرار المؤلف وسلوك الواجهة.

## الاسترداد الواعي بالحصة (v0.3.10)

لا يعيد عامل Gemini النداء داخليًا عند 429/503/504 أو المهلة. يسجل الفشل المؤقت في المهمة الدائمة، ثم يقرأ منسق الواجهة الحالة من قاعدة البيانات ويطبق backoff متدرجًا. يعمل التوازي التشغيلي بمفردة واحدة، وعند الضغط يتوقف الإطلاق حتى موعد الاسترداد، ويمنع إطلاق مفردات جديدة حتى نهاية نافذة التهدئة. قاعدة البيانات تسمح بثلاث محاولات نقل متدرجة، ويمكن للمستخدم بدء دورة محاولات جديدة يدويًا للمفردة الفاشلة.


### Checkpoint المؤلف
بعد نجاح نداء المؤلف تحفظ المفردة المؤلفة مؤقتًا في `author_checkpoint`. أخطاء النقل أثناء المراجعة لا تعيد التأليف، بينما أخطاء المحتوى تمسح الـcheckpoint كي تبدأ محاولة محتوى جديدة نظيفة.

### Retry time
يحفظ `retry_after_at` في قاعدة البيانات، ولا تسمح دالة claim بحجز المفردة قبل الموعد. أخطاء النقل تعكس زيادة `attempt_count` التي حصلت عند claim، لذلك لا تُستهلك ميزانية السؤال بسبب انقطاع المزود.

### Provider protocol v1
لا تسبق الدورة أي نداء Gemini تجريبي. `health` يفحص توافق Worker وعقد قاعدة البيانات فقط، ثم تُنشأ/تستأنف الدورة الدائمة مباشرة. أول مفردة حقيقية هي بوابة المزود: يبدأ الإرسال بتوازي 1، وبعد أول `ready` يسمح المنسق بالتوازي الطبيعي. أخطاء HTTP غير المؤقتة توقف بقية الإرسال بعد أول مفردة، بينما 429/5xx/timeout تدخل `transport_backoff` داخل المهمة نفسها.


## Runtime Contract v0.3.12

أخطاء النقل المؤقتة لا تمر من دالة قادرة على إنهاء المفردة. `defer_assessment_generation_item_v1` مسؤول حصريًا عن 429/503/timeout، بينما `fail_assessment_generation_content_v1` مسؤول عن فشل المحتوى. يفحص Worker عقد قاعدة البيانات في `health` وعند معالجة المفردة، ويستخدم Jobs استردادًا versioned للـ stale leases.

## Thin Item Contract + Typed Visual Planner (v0.3.14)

المشكلة التي يعالجها هذا الإصدار هي تضخم Structured Output الرئيسي: كان عقد التأليف يجمع في استجابة واحدة نص السؤال وكل حقول جميع أنواع المرئيات، ثم يعيد المراجع العقد الضخم نفسه داخل `finalItem`. الإصدار الحالي يفصل المسؤوليات:

```text
Author thin schema
  stimulus + text + options + answer + rationale + markScheme + visualIntent
        ↓
Reviewer thin schema
        ↓
Deterministic/science validation
        ↓
visualIntent.mode = none / illustration_2d ؟
  نعم → لا Visual Planner منظم
  لا  → Typed Visual Planner schema خاص بالنوع وحده
        ↓
Deterministic renderer
```

- مخطط `force_diagram` لا يعرف حقول الدوائر أو الجداول أو الأشعة؛ يحصل فقط على المتجهات والنقاط والساق/المسار والأبعاد والتعليقات اللازمة.
- مخطط `circuit_diagram` لا يعرف هندسة القوى؛ يحصل فقط على المكونات والتعليقات.
- الرسوم البيانية والجداول تحصل على مخططها الأصغر الخاص بها.
- `illustration_2d` يبقى مشهدًا سياقيًا في مسار الصور الحالي ولا يُجبر على هندسة Structured Output.
- health يعلن `visualContractVersion=3`, `thinItemContractVersion=1`, `visualPlannerVersion=2`, `providerProtocolVersion=5`، ويمنع العميل بدء الدورة إذا كان Worker المنشور أقدم.
- لا تغيير في Runtime Contract لقاعدة البيانات في v0.3.14؛ قاعدة v0.3.12 تبقى العقد المعتمد.

## Durable First-Item Provider Gate (v0.3.15)

- لا يستدعي مسار البدء أو الاستئناف `preflight` للمزود.
- `health` محلي بالنسبة للمزود: يفحص هوية العامل وعقد قاعدة البيانات ولا يستهلك طلب Gemini.
- المنسق يطلق أول مفردة وحدها حتى يثبت مسار Author → Reviewer → Validation على طلب حقيقي محفوظ.
- بعد أول `ready` يمكن للتوازي العودة إلى القيمة التشغيلية الطبيعية، وعند ضغط المزود يبقى التوازي 1.
- timeout/429/503 تحدث بعد claim لمفردة دائمة، ولذلك تدخل `defer_assessment_generation_item_v1` بدل أن تمنع إنشاء الدورة.
- `preflight` الموجود في Edge بقي تشخيصيًا/توافقيًا فقط ولا يتصل بـGemini، ولا تستدعيه الواجهة الحالية.

## Local-Validated Visual Planner (v0.3.14)

- سجل التشغيل أثبت أن `preflight_visual_planner` كان وحده يعيد HTTP 400 بينما نجح الاتصال والعقدان النحيفان.
- لذلك لا يرسل Visual Planner مخطط JSON Schema هندسيًا إلى Gemini. يطلب JSON خفيفًا فقط (`responseMimeType=application/json`) ويصف الشكل المتوقع في التعليمات.
- واثق يعامل الخرج كبيانات غير موثوقة: JSON.parse → normalizeVisual → validateContent → buildVisualSpec. لا يصل أي مرئي ناقص أو غير متسق إلى النتيجة الجاهزة.
- preflight العام لا يشغّل Visual Planner؛ المسار الاختياري لا يحق له حجب دورة اختبار كاملة.

## Adaptive Parallel Generation — 0.3.17

المسار التشغيلي: أول مفردة منفردة → أول `ready` → حتى مفردتين بالتوازي. عند وجود إشارة ضغط مؤقتة من المزود يهبط المنسق إلى مفردة واحدة، ويظل التأجيل داخل `retry_pending`. بعد زوال إشارة الضغط من الـsnapshot يستعيد التوازي 2 تلقائيًا. هذا توازٍ محافظ للـthroughput ولا يغيّر ترتيب Author/Reviewer داخل المفردة الواحدة.
